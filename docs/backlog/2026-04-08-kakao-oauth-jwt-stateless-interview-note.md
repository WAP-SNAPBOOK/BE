# 카카오 OAuth, JWT, Stateless API 설계 설명 노트

작성일: `2026-04-08`

## 목적

면접에서 아래 질문에 일관되게 답하기 위한 요약 노트다.

- 왜 카카오 OAuth에서 프론트가 인증 화면 진입과 콜백 수신을 맡도록 했는가
- 왜 API 서버를 `stateless`하게 유지하려 했는가
- 왜 `JWT`를 선택했는가
- 그 선택의 트레이드오프는 무엇인가

---

## 한 줄 요약

현재 구조는 `카카오 OAuth 브라우저 흐름은 프론트가 맡고`, 백엔드는 `인가 코드 교환 + 내부 JWT 발급 + API 인증`에 집중하는 설계다.  
즉 `외부 OAuth`와 `우리 서비스 인증`을 분리하고, API 서버는 세션 대신 토큰 검증 중심의 `stateless API`로 유지하려는 선택이다.

## 현재 구현 기준 사실

### 1. 카카오 로그인 엔드포인트는 `accessCode`를 받는다

백엔드는 카카오 인가 코드를 직접 받아 처리하는 API를 제공한다.

- `POST /oauth/login/kakao`
- `POST /oauth/login/kakao/local`

관련 코드:

- `src/main/java/com/example/easybooking/auth/presentation/AuthController.java`
- `src/main/java/com/example/easybooking/auth/service/AuthService.java`

### 2. 백엔드는 카카오 토큰 교환과 사용자 조회 뒤 우리 토큰을 발급한다

흐름은 아래와 같다.

1. 프론트가 카카오에서 `accessCode`를 받는다.
2. 백엔드가 해당 코드로 카카오 토큰을 교환한다.
3. 카카오 사용자 식별값을 조회한다.
4. 우리 서비스 사용자와 매핑한다.
5. 기존 회원이면 `accessToken`, `refreshToken`을 발급한다.
6. 미가입이면 `TEMP` 성격의 임시 토큰을 발급한다.

관련 코드:

- `src/main/java/com/example/easybooking/auth/util/KakaoOAuthProvider.java`
- `src/main/java/com/example/easybooking/auth/util/JwtUtil.java`

### 3. API 인증은 세션이 아니라 JWT 검증으로 복원한다

Spring Security 설정은 세션을 `STATELESS`로 두고, 매 요청마다 `Authorization: Bearer ...` 헤더의 JWT를 검증한다.

관련 코드:

- `src/main/java/com/example/easybooking/auth/SecurityConfig.java`
- `src/main/java/com/example/easybooking/auth/JwtAuthenticationFilter.java`

### 4. 공유 링크와 OAuth redirect 흐름은 프론트 앱을 향한다

운영 설정 기준으로 카카오 redirect는 프론트 `/auth`로 향하고, 공유 링크도 백엔드가 최종 화면을 렌더링하지 않고 프론트 `/s/{slugOrCode}`로 `302` 리다이렉트한다.

관련 코드/설정:

- `src/main/resources/application.yml`
- `src/main/java/com/example/easybooking/link/ShortLinkController.java`

## SPA 구조라고 본 근거

엄밀히 말하면 이 백엔드 저장소만 보고 프론트 구현 방식을 `100% 단정`할 수는 없다.  
하지만 현재 저장소 기준으로는 `분리 배포된 SPA형 프론트`라고 보는 근거가 충분히 강하다.

### 근거

- 프론트 주소가 백엔드와 별도 오리진으로 잡혀 있다.
    - 로컬: `http://localhost:5173`
    - 운영: `https://ssnapbook.netlify.app`
- 카카오 OAuth redirect가 백엔드 HTML이 아니라 프론트 `/auth` 경로로 향한다.
- 공유 링크 `GET /s/{slugOrCode}`도 서버 렌더링 대신 프론트 경로로 `302` redirect 한다.
- CORS 설정이 별도 프론트 오리진과 `Authorization` 헤더 기반 호출을 전제로 한다.
- `build.gradle`에 `Thymeleaf`, `Mustache` 같은 서버 템플릿 엔진 의존성이 없다.
- `src/main/resources` 아래에도 템플릿 파일이 없다.
- `@Controller` 사용처 중 확인된 `ChatController`는 HTML 렌더링이 아니라 WebSocket 메시지 처리용이다.

### 면접에서 안전한 표현

`이 저장소만 기준으로 보면, 프론트가 별도 앱으로 분리되어 라우팅과 화면 상태를 주도하는 SPA형 구조로 추론할 수 있다`라고 말하는 것이 가장 안전하다.

## 왜 SPA를 선택했는가

이 질문은 `왜 프론트 기술로 SPA를 골랐는가`이면서 동시에 `왜 서비스 전체를 그런 클라이언트 아키텍처로 가져갔는가`에 대한 질문이다.

즉 이건 순수하게 프론트 구현 취향의 문제라기보다, `제품 UX`, `클라이언트 구조`, `백엔드 API 설계`가 같이 맞물린 선택으로 설명하는 편이 좋다.

### 면접에서의 안전한 전제

현재 저장소만으로 `당시 팀이 왜 SPA를 최종 선택했는지`를 역사적으로 단정할 수는 없다.  
그래서 면접에서는 `이 서비스 특성과 현재 구조를 기준으로 보면, SPA 선택 이유는 이렇게 설명할 수 있다`라고 말하는 편이 안전하다.

### 설명 논리

1. 로그인 이후 상호작용이 많은 앱형 화면이 많다.
    - 예약 진입
    - 직원 선택
    - 시간 슬롯 조회
    - 입력 폼 조합
    - 채팅

2. 이런 흐름은 전체 페이지를 매번 새로 그리는 방식보다, 클라이언트가 상태를 유지하면서 필요한 데이터만 API로 가져오는 방식과 잘 맞는다.

3. 프론트와 백엔드를 분리하면 병렬 개발과 독립 배포가 쉬워진다.
    - 프론트는 화면/라우팅/상태 관리에 집중
    - 백엔드는 인증/비즈니스/API 계약에 집중

4. API를 재사용 가능한 형태로 정리하기 좋다.
    - 웹 외 다른 클라이언트가 붙더라도 같은 API와 인증 모델을 재사용하기 쉽다.

5. 이 서비스는 공개 콘텐츠 SEO보다는 로그인 후 사용자의 상호작용과 상태 전환이 더 중요하다.
    - 따라서 서버 HTML 렌더링보다 앱형 UX가 더 중요한 쪽에 가깝다.

### 그래서 이건 프론트 논리인가

반은 맞고 반은 아니다.

- `SPA가 더 자연스러운 UX를 만든다`는 점은 프론트/제품 논리다.
- `그 전제에서 백엔드를 stateless API로 맞춘다`는 점은 백엔드/플랫폼 논리다.

즉 `SPA 선택`은 프론트만의 로컬 최적화가 아니라, 클라이언트와 서버의 역할 분리를 포함한 전체 구조 결정으로 설명하는 것이 좋다.

### 백엔드 관점에서 이어지는 논리

클라이언트가 라우팅과 화면 상태를 주도하는 구조라면, 백엔드는 세션으로 브라우저 상태를 관리하기보다 다음 역할에 집중하는 편이 자연스럽다.

- 데이터 API 제공
- 토큰 발급
- 토큰 검증
- 권한 확인
- 비즈니스 규칙 처리

즉 `SPA를 선택했기 때문에 stateless API를 무조건 써야 한다`가 아니라,  
`SPA형 구조에서는 stateless API가 책임 분리 측면에서 더 잘 맞는다`가 더 정확한 표현이다.

### 대안과 비교

아래 같은 경우는 SSR 또는 하이브리드가 더 맞을 수 있다.

- SEO가 핵심인 공개 콘텐츠 서비스
- 최초 렌더링 속도가 매우 중요한 서비스
- 서버가 페이지 조합과 브라우저 흐름을 강하게 통제해야 하는 서비스

반대로 현재처럼 예약, 관리, 채팅처럼 로그인 이후 상호작용이 많은 앱형 서비스는 SPA 논리가 더 자연스럽다.

### 면접용 답변 예시

`SPA는 프론트 기술 취향이라기보다 서비스 UX와 클라이언트 구조에 대한 선택이라고 봤습니다. 저희 서비스는 로그인 이후 예약, 직원 선택, 시간 슬롯 조회, 채팅처럼 상태 변화가 많은 화면이 많아서 SPA가 잘 맞았습니다. 그 전제에서 백엔드는 세션으로 브라우저 상태를 들고 있기보다, JWT를 검증하는 stateless API로 두는 게 역할 분리와 운영 측면에서 더 일관적이라고 판단했습니다.`

## 왜 프론트가 카카오 인증 화면 진입과 콜백 수신을 맡는가

핵심은 `브라우저 이동 책임`과 `API 서버 책임`을 분리한 것이다.

### 선택 이유

1. 브라우저 흐름은 프론트가 더 잘 안다.
    - 로그인 후 원래 가려던 페이지 복귀
    - 에러 화면 처리
    - 로딩/실패/재시도 UI
    - 라우트 전환과 상태 복원

2. 백엔드는 API 서버 역할에 집중할 수 있다.
    - 인가 코드 검증
    - 카카오 토큰 교환
    - 사용자 식별 및 회원 매핑
    - 우리 JWT 발급

3. 외부 OAuth와 내부 인증을 분리할 수 있다.
    - 카카오는 로그인 순간에만 사용
    - 이후 비즈니스 API는 우리 JWT만 사용

4. 프론트와 백엔드가 분리 배포된 구조와 잘 맞는다.
    - 화면 진입점은 프론트
    - 데이터/인증 API는 백엔드

### 대안과 비교

백엔드가 카카오 콜백을 직접 받아도 된다.  
다만 그 경우 서버가 아래 책임을 더 많이 져야 한다.

- redirect state 관리
- 로그인 후 추가 redirect
- 세션 또는 중간 상태 저장
- 프론트 화면 복귀 흐름 제어

즉 `서버 사이드 렌더링`, `BFF`, `서버가 브라우저 흐름을 강하게 통제하는 구조`라면 백엔드 콜백 방식이 더 잘 맞을 수 있다.  
하지만 현재처럼 프론트가 화면을 주도하는 구조에서는 프론트가 브라우저 OAuth 흐름을 맡는 쪽이 자연스럽다.

## 왜 API 서버를 Stateless하게 유지하려 했는가

여기서 `stateless`는 `서버가 사용자 로그인 상태를 세션 저장소에 들고 있지 않는다`는 뜻이다.

### 장점

1. 서버 역할이 단순해진다.
    - 각 요청은 자기 인증 정보(`JWT`)를 들고 온다.
    - 서버는 토큰만 검증하면 된다.

2. 수평 확장과 운영이 쉬워진다.
    - 세션 공유 저장소가 필수는 아니다.
    - 어느 인스턴스가 요청을 받아도 같은 방식으로 처리할 수 있다.

3. 프론트와 백엔드 책임이 더 선명해진다.
    - 프론트: 라우팅, 화면 상태, 로그인 후 복귀
    - 백엔드: 토큰 발급, 토큰 검증, 권한 확인, 비즈니스 처리

4. OAuth와 내부 인증을 분리하기 쉽다.
    - 카카오 로그인 결과를 내부 JWT로 바꾸고 나면
    - 이후 API는 카카오에 덜 결합된다.

5. 다른 채널에도 같은 인증 모델을 재사용할 수 있다.
    - 현재 코드도 HTTP API와 WebSocket 인증에 JWT를 공통 사용한다.

### 왜 SPA형 구조에서 특히 더 자연스러운가

SPA에서는 화면 전환과 UI 상태가 프론트에 남아 있고, 서버는 주로 JSON API를 제공한다.  
즉 서버가 사용자의 화면 상태나 로그인 세션을 계속 붙잡고 있을 필요가 줄어든다.

그래서 `프론트가 화면을 주도하고, 백엔드는 요청 단위로 인증을 복원하는 구조`가 잘 맞는다.

---

## 왜 JWT를 선택했는가

JWT는 현재 구조의 `stateless API`를 구현하기 위한 수단이다.

### 선택 이유

1. 세션 없이 사용자 인증 정보를 요청마다 전달할 수 있다.
2. `role`, `type(access/refresh/TEMP)` 같은 최소 클레임을 함께 담을 수 있다.
3. 프론트와 백엔드가 분리된 구조에서 `Authorization` 헤더 기반 인증에 잘 맞는다.
4. HTTP API와 WebSocket 인증에 같은 토큰 모델을 재사용하기 쉽다.
5. 가입 직전 상태 같은 과도기 상태도 별도 세션 없이 표현할 수 있다.
    - 현재 구현은 `TEMP` 토큰을 사용한다.

### 현재 구현에서의 사용 방식

- `access token`
    - 일반 API 호출용
- `refresh token`
    - access token 재발급용
- `TEMP token`
    - 소셜 로그인 직후 미가입 사용자의 회원가입 진행용

즉 JWT는 단순 로그인 토큰이 아니라, 현재 시스템의 인증 상태 모델 자체를 표현하는 도구로 쓰이고 있다.

---

## 이 선택의 트레이드오프

`stateless + JWT`는 단순하고 확장성 있는 구조지만, 공짜는 아니다.

### 비용과 단점

1. 강제 로그아웃과 즉시 폐기가 어렵다.
    - 세션은 서버에서 바로 끊으면 끝난다.
    - JWT는 만료 전까지 살아있을 수 있다.

2. 권한 변경 반영이 늦을 수 있다.
    - 토큰 안의 role이 발급 시점 기준일 수 있다.

3. 매 요청마다 토큰 검증 비용이 든다.
    - 세션 조회 대신 서명 검증을 수행한다.

4. 클라이언트 저장 전략이 중요해진다.
    - 어디에 저장할지에 따라 XSS/CSRF 대응 전략이 달라진다.

5. refresh token 관리가 단순하면 보안 제어력이 낮아진다.
    - rotation
    - blacklist
    - 재사용 감지
    - 기기별 세션 관리
      같은 보완이 필요할 수 있다.

### 그래서 어떻게 말하면 좋은가

`단순성, 분리, 확장성을 얻는 대신, 토큰 폐기 제어와 세밀한 세션 관리 능력은 약해진다`고 설명하면 된다.

## 면접용 핵심 답변 예시

### 30초 버전

`저희는 프론트와 백엔드가 분리된 구조였기 때문에, 카카오 OAuth의 브라우저 이동과 콜백 수신은 프론트가 맡고 백엔드는 인가 코드 교환과 내부 JWT 발급만 담당하도록 나눴습니다. 이후 API 서버는 세션을 저장하지 않고 각 요청의 JWT만 검증하는 stateless 구조로 유지했습니다. 이렇게 하면 프론트는 화면 상태와 로그인 후 복귀를 일관되게 처리할 수 있고, 백엔드는 확장성과 운영 단순성을 가져갈 수 있습니다. 대신 강제 로그아웃이나 토큰 폐기 제어는 세션 방식보다 약하다는 트레이드오프가 있습니다.`

### 1분 버전

`핵심은 외부 OAuth와 내부 인증을 분리한 겁니다. 카카오 로그인 자체는 브라우저 중심 흐름이라서, 프론트가 인증 화면 진입과 콜백 수신을 맡도록 했습니다. 그 다음 백엔드는 전달받은 인가 코드로 카카오 토큰을 교환하고 사용자 식별값을 확인한 뒤, 우리 서비스에서 쓸 JWT를 발급합니다. 이후 모든 API는 카카오 토큰이 아니라 우리 JWT로 인증합니다. 이렇게 하면 API 서버는 세션을 들고 있지 않아도 되고, 매 요청에서 JWT만 검증하면 되기 때문에 stateless하게 운영할 수 있습니다. 프론트와 백엔드의 책임 분리가 명확해지고, 여러 인스턴스로 확장하기도 쉬워집니다. 다만 JWT는 세션보다 즉시 폐기나 강제 로그아웃이 어렵기 때문에, 짧은 access token과 refresh token 정책 같은 보완이 필요합니다.`

---

## 말할 때 주의할 점

- `SPA라서 무조건 stateless가 정답`이라고 말하면 과하다.
- 더 정확한 표현은 `분리된 프론트가 화면 흐름을 주도하는 구조에서는 stateless API가 더 자연스럽다`이다.
- `백엔드 콜백 방식이 틀렸다`가 아니라 `우리 구조에서는 프론트 콜백 방식이 더 적합했다`라고 말하는 편이 좋다.
- `JWT가 무조건 더 안전하다`가 아니라 `세션보다 운영과 확장, 책임 분리에 유리하지만 폐기 제어는 약하다`라고 말하는 편이 균형 있다.
