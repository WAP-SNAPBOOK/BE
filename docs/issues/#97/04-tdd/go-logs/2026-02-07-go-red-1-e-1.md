## 1) 어떻게 변경할지 (설계/접근 방식)

- `ReservationTimeBlockWriter.saveAll(blocks)`의 행위를 먼저 테스트로 고정한다.
  - 입력: `ReservationTimeBlock` 리스트(30분 단위 블록들)
  - 출력: 모두 저장되어 **id가 할당된** 블록 리스트
- 테스트는 `@DataJpaTest`로 작성하고, Writer를 리포지토리로 직접 생성해 호출한다. (기존 `StaffWriterTest` 패턴)

### RED 단계의 “최소 임시 구현”

- 테스트가 컴파일되도록 아래 최소 구조만 만든다.
  - `ReservationTimeBlock` 엔티티(필드/생성 팩토리/Getter)
  - `ReservationTimeBlockRepository`(JPA repository)
  - `ReservationTimeBlockWriter.saveAll(List<...>)` (임시로 “저장 안 함”)
- 임시 구현은 저장을 수행하지 않아, 테스트에서 기대하는 `id != null` 조건을 만족하지 못해 **실패(RED)** 하게 만든다.

---

## 2) 변경 근거 (이유, 장단점)

- **이유**
  - “확정 시 점유 블록 저장”의 기반이 되는 Writer API를 먼저 안정화해야 이후 단계(UNIQUE 충돌/확정 로직)가 TDD로 자연스럽게 이어진다.
  - `@DataJpaTest`는 실제 DB 라운드트립을 통해 “저장되어 id가 생겼는지”를 가장 작은 단위로 검증할 수 있다.

- **장점**
  - Writer의 계약(저장 + id 할당)을 테스트로 먼저 못 박아, 구현/리팩터링의 안전망이 된다.

- **단점/주의**
  - RED에서는 의도적으로 “저장하지 않게” 만들어 실패시키므로, GREEN에서 반드시 `saveAll()`을 실제 저장으로 바꿔야 한다.

## 3) 코드 수정 예시 (diff 또는 예시 코드)

### (예시) 실패 테스트

```java
@DataJpaTest
class ReservationTimeBlockWriterTest {
  @Autowired ReservationTimeBlockRepository repo;

  @Test
  void saveAll_persistsAllBlocksAndAssignsIds() {
    ReservationTimeBlockWriter writer = new ReservationTimeBlockWriter(repo);
    List<ReservationTimeBlock> blocks = List.of(
        ReservationTimeBlock.create(1L, 10L, LocalDateTime.of(2026,2,5,14,0)),
        ReservationTimeBlock.create(1L, 10L, LocalDateTime.of(2026,2,5,14,30))
    );

    List<ReservationTimeBlock> saved = writer.saveAll(blocks);

    assertThat(saved).hasSize(2);
    assertThat(saved).allSatisfy(b -> assertThat(b.getId()).isNotNull()); // RED: id=null
  }
}
```

### (예시) 임시 구현(RED용)

```java
public List<ReservationTimeBlock> saveAll(List<ReservationTimeBlock> blocks) {
  return blocks; // 저장 안 함 → RED
}
```
