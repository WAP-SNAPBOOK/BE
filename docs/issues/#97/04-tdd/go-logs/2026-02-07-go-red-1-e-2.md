---

## 1) 어떻게 변경할지 (설계/접근 방식)

- `reservation_time_blocks`에 대해 동일 `(staff_id, block_start_at)` 중복 저장이 **DB UNIQUE 위반 예외**로 떨어지는지 테스트로 고정한다.
- 테스트는 `@DataJpaTest`에서 `ReservationTimeBlockRepository.saveAndFlush()`를 사용해,
  - 첫 저장은 성공
  - 두 번째(중복) 저장은 flush 시점에 예외가 발생하도록 만든다.

---

## 2) 변경 근거 (이유, 장단점)

- **이유**
  - “겹침 방지”의 최후 방어선은 DB UNIQUE 제약이므로, 애플리케이션 레벨 로직과 별개로 제약이 실제로 작동하는지 확인해야 한다.
- **장점**
  - 동시성/락 이슈와 무관하게, 중복 점유가 DB 레벨에서 차단됨을 보장한다.
- **주의**
  - 현재 테스트 환경이 Hibernate DDL로 스키마를 만들 경우, UNIQUE 제약이 없으면 예외가 발생하지 않아 테스트가 실패(RED)한다.
  - GREEN에서 엔티티 매핑에 UNIQUE 제약(또는 테스트 스키마에 제약)을 추가해야 한다.

---

## 3) 코드 수정 예시 (diff 또는 예시 코드)

```java
@DataJpaTest
class ReservationTimeBlockUniqueConstraintTest {
  @Autowired ReservationTimeBlockRepository repo;

  @Test
  void save_throwsException_whenDuplicateStaffAndBlockStartAt() {
    repo.saveAndFlush(ReservationTimeBlock.create(1L, 10L, LocalDateTime.of(2026,2,5,14,0)));

    assertThatThrownBy(() ->
        repo.saveAndFlush(ReservationTimeBlock.create(2L, 10L, LocalDateTime.of(2026,2,5,14,0)))
    ).isInstanceOf(DataIntegrityViolationException.class); // RED(현재): 예외가 안 나올 수 있음
  }
}
```

## 4) 변경 후 예상 결과 (동작, 성능, 영향 범위)

- 이번 go(RED) 이후
  - 테스트는 **실패(RED)** 한다 (현재 스키마에 UNIQUE가 없거나 적용되지 않으면 중복 저장이 성공)
- 영향 범위
  - 테스트 1개 추가 (프로덕션 동작 변경 없음)
