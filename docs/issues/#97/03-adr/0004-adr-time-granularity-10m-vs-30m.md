# ADR-0004: 예약 시간 단위(10분 vs 30분) 표준화

## 논리적 흐름 요약

- 현재 #97 관련 산출물에 **10/15/30분 단위가 혼재**되어 있고, 이는 ERD/plan/코드/테스트의 정합성을 깨뜨린다.
- 따라서 “예약 시작 시간 정렬 + duration 검증 + 점유 블록 생성 단위”를 **하나의 기준 단위로 표준화**해야 한다.

---

## 배경 / 문제

- 최종 ERD(`docs/issues/#97/reservation-erd-v2.md`)는 초기 버전에서 30분 단위를 전제로 작성되어 있었으나, 정책 확정에 따라 10분 단위로 정렬한다.
- 반면 현재 구현/테스트와 일부 문서(`plan.md`, 예외 매핑 문서)는 10분 단위를 전제로 동작함.
- 또한 `ReservationTimeBlock` 테이블명 불일치(단수/복수)처럼, 정책 혼재는 운영 데이터 사고로 이어질 수 있다.

---

## 결정이 필요한 항목(Decision)

다음 항목을 같은 단위로 묶어 결정한다.

- `Reservation.start_at`(예약 시작 시각)의 허용 단위
- `Reservation.duration_minutes`의 허용 단위(배수)
- `ReservationTimeBlock.block_start_at` 생성 단위(점유 블록 해상도)

---

## 옵션

### 옵션 A) 10분 단위 유지(현행 구현 기준)

- **정책**: 시작 시간은 10분 단위, duration은 10분 배수, 점유 블록도 10분 단위로 생성
- **장점**
  - 현행 코드/테스트 변경량이 작다.
  - 10분 단위 예약 UX가 가능하다(세밀한 스케줄링).
- **단점**
  - 점유 블록 row 수가 증가(예: 60분 = 6 rows) → 쓰기/유니크 충돌 비용 증가
  - 최종 ERD(30분)와 불일치 → 문서를 “최종안”에서 되돌려야 함

### 옵션 B) 30분 단위로 전환(ERD 최종안 기준) — **추천**

- **정책**: 시작 시간은 30분 단위, duration은 30분 배수, 점유 블록도 30분 단위로 생성
- **장점**
  - ERD 최종안과 구현 정합성 회복
  - 점유 블록 row 수 감소(예: 60분 = 2 rows) → 운영 부하/충돌 가능성 감소
  - 검증/설명이 단순해짐
- **단점**
  - DTO 검증/블록 생성/테스트/문서 다수 변경 필요(행동 변경)
  - 10분 단위 예약은 불가(요구가 있다면 별도 정책 필요)

---

## 결정

**옵션 A(10분 단위)로 표준화**로 확정한다.

근거:
- 현재 코드/테스트/예외 매핑 문서가 10분 단위를 전제로 동작하고 있고,
- 10분 단위 예약 UX가 필요하며,
- ERD/모델링 과정/plan 문서를 10분 단위로 정렬하는 편이 #97 진행 비용/리스크를 낮춘다.

---

## 적용 범위(변경 대상)

옵션 A 채택 시, 최소 변경 대상:

- 문서:
  - `docs/issues/#97/reservation-erd-v2.md`의 30분 표기를 10분 정책으로 정렬
  - `docs/issues/#97/reservation-erd-v2-modeling-process.md`의 15/30분 표기를 10분 정책으로 정렬
- 코드:
  - (현재는 이미 10분 단위 기반) 10분 단위 정책과 어긋난 부분이 있으면 10분 기준으로 정렬
- 테스트:
  - (현재는 이미 10분 단위 기반) 10분 단위 정책과 어긋난 기대값이 있으면 10분 기준으로 정렬
- (필수) 스키마/매핑 정합성:
  - `ReservationTimeBlock` 엔티티 테이블명 `reservation_time_blocks`로 정렬

---

## 결과(기대 효과)

- 문서/plan/코드/테스트가 **동일 단위 정책**으로 일치한다.
- 점유 블록 저장이 단순화되고 충돌 비용이 감소한다.
