## 문제 재정의(한 문장)

Flyway로 ERD v2 스키마(V1~V3)를 적용한 이후에도 애플리케이션 코드는 여전히 레거시 예약 모델(date/time/formDataJson/Slot 등)을 중심으로 동작해, **스키마-코드 불일치와 운영 설정(Flyway/JPA) 리스크**가 커진 상태다.

## 원인 분석

### 가설

- **가설 1**: DB는 ERD v2로 진화했지만, 애플리케이션은 레거시 필드/구조를 계속 참조하고 있어 “이중 세계(dual reality)”가 발생했다.
- **가설 2**: Flyway 운영 옵션(`baseline-on-migrate`) 및 JPA 스키마 관리 옵션(`ddl-auto`)이 “마이그레이션 완료 이후에도” 안전한 상태로 고정되지 않아, 환경/재배포/초기화 시 **예상치 못한 스키마 변형** 가능성이 남아 있다.
- **가설 3**: ERD v2에서 핵심 제약(예: `reservation_time_blocks`의 `UNIQUE(staff_id, block_start_at)`)이 도입되면서, 동시성/충돌 처리 정책을 코드가 아직 흡수하지 못했다.
- **가설 4**: 삭제(FK) 정책이 명확히 확정되지 않아, v2 테이블 확장 시 “부모 삭제 시 자식 FK 충돌”이 운영 장애로 이어질 수 있다.

### 검증(증거/재현/로그/지표)

- **증거(이슈 본문)**: `#97`에 “코드는 아직 레거시 기반(date/time/formDataJson/Slot)이며, 운영 설정 안정화(baseline-on-migrate, ddl-auto validate), v2 전환(시간/스태프/메뉴/입력값/히스토리), 동시성 충돌 처리, 삭제 정책”이 필요하다고 명시되어 있다.
- **재현/확인 체크(권장)**:
  - **Flyway 상태 확인**: `flyway_schema_history`에서 baseline(0) 및 `V1~V3`가 모두 `success=1`인지 확인
  - **기동 로그 확인**: 애플리케이션 기동 시 `V1 -> V2 -> V3` 적용 로그가 정상이며, 재기동 시 재적용/충돌이 없는지 확인
  - **운영 설정 확인**:
    - `baseline-on-migrate`가 “초기 1회용”으로만 사용되고 이후 비활성화(또는 환경별 제한) 되었는지 확인
    - `spring.jpa.hibernate.ddl-auto`가 최종적으로 `validate`(또는 운영에 준하는 안전 모드)로 수렴 가능한지 확인
  - **제약 충돌 지표/로그**: `reservation_time_blocks` 관련 unique 충돌(예: `DuplicateKey`/`ConstraintViolation`) 발생률 및 롤백/재시도/사용자 메시지 흐름 확인
  - **삭제 시나리오**: 예약(부모) 삭제/상태 변경 시 연관 자식 테이블에 대한 FK 오류 발생 여부 확인

### 결론(원인)

근본 원인은 “ERD v2 전환”이 **DB 마이그레이션(Flyway) 단계에서 멈추고**, 애플리케이션이 이를 따라가는 **도메인/데이터 흐름 전환(읽기/쓰기/검증/동시성/삭제정책)**을 아직 완료하지 못해 생긴 **스키마-코드 불일치 + 운영 안정화 미완료**다.

## 대안

### 대안 A: Big-bang 전환(단일 릴리즈에서 v2 완전 이행)

- **개요**: v2 테이블/컬럼을 기준으로 예약 도메인(시간/스태프/서비스/입력값/히스토리/타임블록)을 한 번에 전환하고, 레거시 경로(date/time/formDataJson/Slot)를 즉시 제거하거나 최소화한다.
- **장점**
  - **일관성**: 전환 이후 “단일 진실원천(SSOT)”이 v2로 고정됨
  - **복잡도 감소**: 이중 저장/이중 읽기(dual write/read) 같은 과도기 복잡도 최소
  - **운영 단순화**: 검증 포인트가 명확(전환 전/후)
- **단점**
  - **릴리즈 리스크**: 변경 범위가 넓어 장애/롤백 비용이 큼
  - **테스트/검증 부담**: 동시성(UNIQUE 충돌)·삭제 정책까지 한 번에 흡수해야 함
- **비용**
  - 단기간 높은 개발/테스트 집중 필요(광범위 회귀 테스트, 데이터 정합성 검증)
- **리스크**
  - 배포 직후 예외 케이스(히스토리 누락, 타임블록 생성 타이밍, FK 삭제 충돌)로 장애 가능
- **운영 난이도**
  - 전환 시점에는 높음(전환 후에는 낮아짐)

### 대안 B: 단계적 전환(호환 계층 유지 + Phase 단위로 v2 흡수)

- **개요**: 이슈에 명시된 우선순위(운영 안정화 → 예약 핵심(시간/스태프/타임블록) → 메뉴/입력값/히스토리 → Slot Phase 4)를 따라, 각 단계에서 **기능 단위로 v2로 전환**한다. 레거시 필드는 일정 기간 “읽기 호환/쓰기 중단” 등 정책으로 점진 제거한다.
- **장점**
  - **릴리즈 안전성**: 변경을 쪼개 장애 범위를 축소
  - **관측 가능**: 단계별 지표/로그로 안정성 확인 후 다음 단계 진행 가능
  - **팀 협업 용이**: 우선순위(AC-3 → AC-4 → AC-6)에 따라 병렬 작업 설계 가능
- **단점**
  - **과도기 복잡도**: 레거시/신규 모델 동시 관리(매핑/변환/검증) 필요
  - **일시적 중복**: 일부 데이터 구조가 중복 유지될 수 있음
- **비용**
  - 중기적으로 총비용 증가(호환 계층 유지/제거 비용) 가능
- **리스크**
  - 전환 기간이 길어지면 “두 세계” 상태가 장기화되어 개발 속도 저하
  - dual write를 선택할 경우 정합성 버그 위험 증가
- **운영 난이도**
  - 중간(단계별로 관리 포인트 존재)

### 대안 C: DB 호환 레이어(뷰/호환 컬럼/트리거)로 앱 변경 최소화

- **개요**: 애플리케이션 변경을 최소화하기 위해 DB에 “레거시 호환”을 제공(예: 뷰, 계산 컬럼, 제한적 트리거)하여, 앱은 천천히 v2로 이동한다.
- **장점**
  - **단기 속도**: 앱 변경량을 줄여 빠르게 운영 안정화 가능
  - **장애 회피**: 즉시 큰 코드 변경 없이도 일부 기능을 유지 가능
- **단점**
  - **DB 복잡도**: 트리거/뷰는 디버깅이 어렵고 성능/락 이슈를 유발할 수 있음
  - **책임 전가**: 도메인 규칙이 DB로 이동해 테스트/유지보수가 어려워짐
- **비용**
  - DB 스크립트/운영 지식 필요, 장기 유지비 상승 가능
- **리스크**
  - 트리거/뷰로 인한 예측 불가 동작, 성능 저하, 마이그레이션 충돌
- **운영 난이도**
  - 높음(관측/튜닝/장애 대응 난이도 상승)

## 추천안

**추천: 대안 B(단계적 전환)**  
이슈 `#97`은 이미 “우선순위(AC-3 → AC-4 → AC-6) + 운영 안정화(AC-1/2) + 삭제/동시성 정책(AC-5/3)”를 명확히 제시하고 있어, 이를 그대로 SSOT로 삼는 **Phase 기반 이행**이 트레이드오프 대비 최선이다.

- **트레이드오프(왜 B가 최선인가)**:
  - A는 전환 속도는 빠르지만, 동시성/삭제/히스토리까지 한 번에 묶이면서 배포 리스크가 과도하게 커진다.
  - C는 단기 편하지만, 장기적으로 DB 복잡도/운영 부담이 커져 “ERD v2 채택”이라는 목적과 충돌한다.
  - B는 과도기 복잡도를 감수하는 대신, **운영 안정화와 도메인 전환을 검증 가능한 단위로 쪼개** 리스크를 통제한다.

## 위험/롤백/관측(Observability) 계획

- **위험**
  - **Flyway 설정 리스크**: `baseline-on-migrate` 유지/오남용 시 기존 DB에 baseline이 잘못 적용될 가능성
  - **JPA ddl-auto 리스크**: 운영 환경에서 `ddl-auto`가 스키마를 변형할 수 있는 설정이면 예기치 않은 변경 위험
  - **동시성/충돌 리스크**: `UNIQUE(staff_id, block_start_at)` 충돌이 사용자 경험/재시도 정책에 영향을 줌
  - **삭제(FK) 리스크**: 부모 삭제 시 자식 FK 충돌로 장애 가능(이슈 AC-5의 A/B 선택 필요)

- **롤백 전략**
  - **단계별 롤백**: Phase 단위로 배포하여, 문제가 발생한 Phase만 되돌릴 수 있도록 범위를 격리
  - **스키마 롤백은 최소화**: 이미 Flyway V1~V3가 적용된 상태이므로, 코드 롤백(기능 플래그/분기) 중심으로 설계
  - **데이터 정합성 복구 절차**: 이중 저장/변환 구간이 있다면, “재계산/재생성(예: time_blocks 재생성)” 스크립트/절차 준비

- **관측(Observability)**
  - **마이그레이션 관측**: 기동 시 Flyway 실행 결과를 명확히 로깅(버전/성공/실패)
  - **제약 충돌 관측**: unique 충돌/ConstraintViolation 예외를 에러코드로 구분하고 발생률을 지표화
  - **핵심 흐름 지표**: 예약 확정(Confirmed) 성공률, 타임블록 생성 성공률/지연, 변경 히스토리 기록 누락률(가능하면 감사 로그)
  - **삭제 실패 관측**: FK 관련 예외 발생 시 traceId로 추적 가능하도록 에러 응답/로그를 연계
