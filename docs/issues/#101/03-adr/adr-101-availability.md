# ADR-101: 예약 가능 시간 관리 아키텍처 결정

## 상태

Proposed (사용자 승인 대기)

## 맥락 (Context)

#101에서 고객은 특정 매장/직원의 예약 가능한 날짜와 시간을 조회해야 하며, 점주는 운영 시간과 휴무일을 설정해야 한다. 기존 #97 ERD v2에서는 예약 생성/확정/점유 관리까지 구현되어 있으나, 예약 가능한 시간대를 정의하고 조회하는 기능은 없다.

## 결정 (Decision)

### D1. 계산 기반 슬롯 조회

- 물리적 슬롯(row 미리 생성) 대신, 운영 시간/휴무일 규칙만 저장하고 조회 시 실시간 계산
- `reservation_time_blocks`가 점유의 SSOT이므로 이중 소스 제거
- 기존 `slots` 테이블은 사용하지 않음

### D2. 정규화된 테이블 구조

- 운영 시간을 요일별 row로 저장 (JSON/캘린더 방식 대신)
- 같은 요일에 복수 row 가능 (휴게시간 지원)
- 운영 시간 `end_time`은 "마지막 예약 가능 슬롯 시각"(inclusive)으로 사용
- 기존 JPA Entity 패턴과 일관성 유지

### D3. 직원 운영 시간 — 요일별 오버라이드

- 매장 기본 운영 시간 + 직원별 요일 단위 오버라이드 (전체 대체 방식 대신)
- 오버라이드 없는 요일은 매장 기본 fallback
- `is_off` 플래그로 특정 요일 안 함 표현
- 직원 시간은 매장 범위 내 축소만 가능

### D4. 매장 레벨 휴무일만

- 직원 개인 휴무는 제외, 매장 단위에서만 관리
- 정기 휴무: 매주/격주(기준날짜)/매달(N번째 주 + 요일)
- 공휴일: 전체 휴무 on/off, 정적 데이터로 시작
- 기타: 특정 날짜 지정

### D5. 매장 단위 예약 간격

- 30분/60분, 매장 전체 통일

### D6. 점주 설정 가능 항목

- 예약 가능 기간: 기본 30일
- 예약 마감 시간: 기본 60분 전
- `schedule_type`: UI 렌더링 힌트 (DAILY/WEEKDAY_WEEKEND/BY_DAY), 저장은 항상 요일별 row
- `schedule_type` 변경 시 기존 운영 시간 전부 삭제 후 교체

### D7. 월 단위 캘린더 조회 계약 추가

- 일 단위 슬롯 조회(`date`)와 별도로 월 단위 조회(`yearMonth`)를 제공
- 월 응답은 `availableDates`, `holidayDates`, `closedDates`를 포함
- 월 경계는 서버 타임존 기준으로 계산하며, `booking_window_days`/`min_booking_lead_minutes`를 동일 적용

## 대안 (Alternatives)

| 결정 | 선택 | 기각된 대안 | 기각 이유 |
|------|------|-------------|-----------|
| D1 | 계산 기반 | 물리적 슬롯 | `reservation_time_blocks`와 이중 소스, 배치 필요 |
| D2 | 정규화 테이블 | JSON 컬럼 | 무결성 제약 어려움 |
| D2 | 정규화 테이블 | 캘린더 사전 생성 | 데이터 중복, 배치 필요 |
| D3 | 요일별 오버라이드 | 전체 대체 | 불필요한 반복 입력, 매장 변경 미반영 |

## 결과 (Consequences)

### 긍정적

- `reservation_time_blocks`만 점유 SSOT — 이중 소스 없음
- 운영 시간/휴무일 변경이 즉시 반영
- 직원 대부분은 매장 기본을 따르므로 데이터 최소화
- 기존 codebase 패턴과 일관성

### 부정적

- 조회 시 계산 로직 필요 (복잡도 증가)
- 특정 시간만 개별 차단 시 별도 테이블 추가 필요

### 리스크

| 리스크 | 대응 |
|--------|------|
| 휴무일 계산 복잡성 (격주, 매달 N째주) | 단위 테스트 철저 |
| 공휴일 데이터 관리 | 정적 데이터로 시작, 연 1회 수동 업데이트 |
| 직원 오버라이드가 매장 범위 초과 | 앱 레벨 검증 |
