## 목적

이 문서는 `#122 서버 오류 즉시 인지 체계`를 검토할 때,
`study/study-system-design` 아래 어떤 문서를 우선 읽어야 하는지,
각 문서에서 무엇을 뽑아와야 하는지,

## 문서별로 파악해야 할 내용

### A. `part2/refined/chap05.md`에서 파악할 것

이 문서에서 뽑아야 하는 핵심은 "감지 시스템"이다.

#### 꼭 파악할 내용

- 모니터링 시스템은 단순 로그 저장이 아니라
  `수집 -> 저장 -> 질의 -> 경보 -> 시각화` 파이프라인이라는 점
- `pull`과 `push` 수집 모델 차이
- 경보 시스템은 임계값 판단만이 아니라
  `중복 억제`, `집계`, `노이즈 제어`까지 포함한다는 점
- 메트릭 시스템에서 비용보다 먼저 실패하는 것이 저장소가 아니라
  `alert fatigue`일 수 있다는 점

#### 이 이슈에 바로 연결되는 해석

- 이번 이슈에서 먼저 필요한 것은 "에러를 어딘가에 저장"하는 것보다
  "누가 감지해서 언제 알려주느냐"를 정하는 일이다.
- 서버 다운은 서버 내부 코드가 아니라 외부 `pull` 기반 체크가 더 적합하다.
- 디스코드 알림은 가능하지만, 중복 억제 없이 바로 붙이면 운영 채널이 망가진다.

#### 이 문서를 읽고 내려야 하는 결정

- 감지 주체를 서버 내부로 둘지 외부 checker로 둘지
- 1차 경보 대상을 `down`, `timeout`, `unexpected exception burst` 중 어디까지 잡을지
- 중복 억제와 샘플링을 이번 이슈 범위에 넣을지

### B. `part1/refined/chap10.md`에서 파악할 것

이 문서에서 뽑아야 하는 핵심은 "알림 채널 설계"다.

#### 꼭 파악할 내용

- 알림 시스템은 채널별 차이를 숨기는 별도 인프라라는 점
- 단일 서버에서 직접 외부 채널로 쏘는 방식의 한계
- 재시도, 중복 방지, 데이터 손실 방지, 운영자 알람의 필요성
- 모니터링 포인트가 단순 성공/실패를 넘어서
  적체량, 성공률, 실패율, 지연시간까지 포함된다는 점

#### 이 이슈에 바로 연결되는 해석

- `Discord webhook`은 "예외 발생 코드 안에서 바로 HTTP 호출"로 끝낼 일이 아니다.
- 최소한 요청 처리 경로와 알림 전송 경로를 분리하거나,
  실패/중복을 감안한 설계가 필요하다.
- 1차 구현에서는 완전한 큐 기반까지 가지 않더라도,
  "비동기 분리", "중복 억제", "재시도 정책"을 의식하고 시작해야 한다.

#### 이 문서를 읽고 내려야 하는 결정

- 직접 동기 전송을 허용할지
- 실패 시 무시할지, 재시도할지
- `unexpected exception`만 알릴지, `business exception`까지 포함할지

### C. `part1/refined/chap03.md`에서 파악할 것

이 문서에서 뽑아야 하는 핵심은 "설계 범위 확정 방식"이다.

#### 꼭 파악할 내용

- 질문 없이 바로 설계에 들어가면 범위가 엇나간다는 점
- 먼저 요구사항, 가용성 제약, 외부 서비스 사용 가능 여부를 확정해야 한다는 점
- 상세 설계보다 먼저 큰 그림과 범위를 맞춰야 한다는 점

#### 이 이슈에 바로 연결되는 해석

- 이번 이슈에서 먼저 확정해야 할 질문은 아래다.
    - 서버 다운까지 잡아야 하는가
    - 앱 내부 `5xx`만 잡아도 되는가
    - 외부 서비스 사용이 가능한가
    - 운영용 health endpoint를 새로 둘 수 있는가
- 이 질문이 정해지지 않으면
  `외부 헬스체커`, `예외 추적 서비스`, `직접 Discord notifier` 중 무엇이 맞는지 결론이 흔들린다.

## 이번 이슈에 필요한 핵심 지식만 압축하면

### 1. 감지와 전달은 분리해서 봐야 한다

- 감지:
    - 서버 다운, timeout, 응답 실패를 누가 발견하는가
- 전달:
    - 발견한 사실을 디스코드로 어떻게 전달하는가

이번 이슈는 이 둘을 섞지 말아야 한다.

### 2. 서버 다운 감지는 외부가 유리하다

- 서버 내부 `ExceptionHandler`는 서버가 살아 있을 때만 동작한다.
- 따라서 "내가 로그를 안 봐도 서버 다운을 바로 아는가"라는 질문에는
  외부 헬스체커가 더 직접적인 답이다.

### 3. 예외 알림은 `unexpected exception`만 먼저 잡아야 한다

- 이 프로젝트는 의도된 `4xx`, `409` business exception이 많다.
- 이것까지 운영 알림에 넣으면 거의 바로 노이즈가 된다.

### 4. 디스코드는 감지기가 아니라 채널이다

- 디스코드 webhook은 마지막 전달 수단이다.
- 감지 기준과 중복 억제 기준을 먼저 정하고 붙여야 한다.

### 5. 알림 품질은 "빨리 옴"보다 "쓸 만하게 옴"이 더 중요하다

- 중복 폭주
- 정상 예외 오탐
- 재시도 무한 루프
- 장애 상황에서 전송 실패

이 네 가지를 막지 못하면 알림은 금방 무시된다.

## 이번 이슈에서 당장 불필요한 내용

아래는 스터디 문서에 나오더라도 이번 이슈 1차 범위에서는 후순위다.

- 시계열 저장소의 장기 retention 최적화
- 다운샘플링과 압축
- 클릭률, 오픈율, 전환율 같은 제품 지표
- 다채널 알림(`SMS`, `이메일`, `푸시`) 전체 확장
- 완전한 큐 기반 대규모 알림 인프라

이번 이슈는 우선
`서버가 죽었는지/큰 오류가 났는지 내가 먼저 아는가`
까지만 해결하면 된다.

## 문서를 읽고 나면 답할 수 있어야 하는 질문

- 이번 이슈의 1차 목표는 `다운 감지`인가 `예외 추적`인가
- 감지는 외부 `pull`인가 내부 `push`인가
- 디스코드 알림은 동기 전송인가 비동기 전송인가
- 어떤 에러까지 운영 알림에 포함할 것인가
- 중복 억제와 재시도를 이번 이슈에 포함할 것인가
- 보안상 health endpoint를 어떻게 노출할 것인가
