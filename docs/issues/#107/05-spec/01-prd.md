# `reservation` PRD

작성일: `2026-03-10`

## 1. 문서 목적

이 문서는 네일샵 예약 기능이 제품 차원에서 어떤 문제를 해결해야 하고, 사용자에게 어떤 경험을 제공해야 하며, 어떤 범위까지 지원해야 하는지를 정의한다.

상세 상태 전이, 도메인 규칙, 에러 코드, API 계약은 별도 문서에서 정의한다.

## 2. 제품 배경

네일샵 예약은 단순한 시간 선택 기능이 아니라 다음 요소를 함께 다뤄야 한다.

- 고객이 실제 예약 가능한 시간만 선택할 수 있어야 함
- 점주가 예약 요청을 검토하고 운영 상황에 맞게 확정/거절/수정할 수 있어야 함
- 예약 취소 정책과 환불 정책이 운영 현실에 맞아야 함
- 예약 시점의 요청사항, 메뉴 선택, 입력값이 이후에도 보존되어야 함

현재 시스템은 기본 예약 생성/확정/거절 흐름은 있으나, 제품 관점에서 필요한 정책과 사용자 경험이 완전히 정리되어 있지 않다.

## 3. 해결하려는 문제

### 고객 문제

- 예약 가능한 시간을 믿고 선택하고 싶다.
- 예약 요청 시 원하는 메뉴, 참고 이미지, 요청사항을 함께 전달하고 싶다.
- 예약 상태가 어떻게 진행되는지 알고 싶다.
- 취소 가능 여부와 취소 정책을 명확히 알고 싶다. v

### 점주 문제

- 실제 운영 가능한 예약만 받고 싶다.
- 예약 요청을 검토해 확정/거절/취소/수정할 수 있어야 한다.
- 고객이 당일 방문이 어려운 경우 운영상 슬롯을 비우고 일정 관리가 가능해야 한다.
- 예약 시점 정보가 유지되어 고객과 커뮤니케이션할 때 혼선이 없어야 한다.

## 4. 제품 목표

- 고객이 유효한 예약 가능 시간에 대해 예약 요청을 생성할 수 있게 한다.
- 점주가 예약을 검토하고 확정/거절/취소/수정할 수 있게 한다.
- 예약 상태와 취소 정책을 명확히 하여 운영 혼선을 줄인다.
- 테스트와 리팩터링의 기준이 되는 제품 요구사항을 확정한다.

## 5. 사용자

- 고객
- 점주

## 6. 핵심 사용자 흐름

### 6.1 고객 예약 생성

고객은 샵, 직원, 날짜, 시간을 선택하고 필요한 요청사항과 메뉴 정보를 함께 제출해 예약 요청을 생성할 수 있어야 한다.

제품 요구사항:

- 고객은 실제 예약 가능한 슬롯에 대해서만 예약 요청을 생성할 수 있어야 한다.
- 예약 요청은 `PENDING` 상태로 생성된다.
- 동일 슬롯에 여러 `PENDING` 요청이 존재할 수 있다.
- 고객은 요청사항, 이미지, 메뉴 선택, 메뉴 입력값을 함께 제출할 수 있다.

### 6.2 점주 예약 처리

점주는 들어온 예약 요청을 보고 확정하거나 거절할 수 있어야 한다.

제품 요구사항:

- 점주는 예약을 확정할 때 시술 시간을 결정할 수 있어야 한다.
- 확정된 예약은 실제 점유 시간으로 관리되어야 한다.
- 점주는 부적절하거나 수용 불가능한 요청을 거절할 수 있어야 한다.

### 6.3 예약 취소

고객과 점주 모두 운영 정책 안에서 예약을 취소할 수 있어야 한다.

제품 요구사항:

- 고객은 예약일 전날 `23:59:59`까지 취소할 수 있어야 한다.
- 고객은 예약일 당일에는 셀프 취소할 수 없다.
- 점주는 당일에도 운영상 취소 처리할 수 있어야 한다.
- 취소 시 환불 가능 여부를 판단할 수 있는 정보가 남아야 한다.
- 서비스는 예약금 자체를 직접 처리하지 않는다.

### 6.4 점주 예약 수정

점주는 운영상 필요에 따라 예약 정보를 수정할 수 있어야 한다.

제품 요구사항:

- 점주는 날짜, 시간, 직원, 요청사항, 이미지, 메뉴, 입력값을 수정할 수 있어야 한다.
- 이미 확정된 예약을 수정하더라도 운영 충돌이 없도록 점유가 재계산되어야 한다.

### 6.5 예약 조회

고객과 점주는 각자 필요한 예약 정보를 조회할 수 있어야 한다.

제품 요구사항:

- 고객은 자신의 예약 목록과 상세를 조회할 수 있어야 한다.
- 점주는 샵 예약 목록과 상세를 조회할 수 있어야 한다.
- 예약 상세에서는 요청사항과 메뉴/입력값 스냅샷이 보존되어야 한다.
- 예약 목록은 핵심 상태와 일정 중심으로 간결해야 한다.

## 7. 범위

### 이번 범위

- 예약 생성
- 예약 상세/목록 조회
- 점주 확정
- 점주 거절
- 고객/점주 취소
- 점주 수정
- 취소 메타데이터 관리
- 예약 가능 시간 연계

### 이번 범위 제외

- 예약금 결제/환불 직접 처리
- `COMPLETED`, `NO_SHOW` 실제 기능 구현
- 통계/정산/패널티 관리

## 8. 제품 정책 요약

- 예약 가능 여부 판단은 `availability` 도메인이 담당한다.
- `reservation` 도메인은 예약 상태와 예약 데이터 관리를 담당한다.
- 당일 연락 후 점주가 슬롯을 비우는 경우는 취소로 본다.
- 연락 없이 방문하지 않은 경우의 `NO_SHOW`는 후속 확장으로 남긴다.
