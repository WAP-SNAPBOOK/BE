# Clarify Feature Specs

## Overview

이 스킬은 대충 떠오른 기능 아이디어를 바로 문서로 찍어내는 용도가 아니다.
먼저 질문으로 모호함을 줄이고, 점진적으로 다음 4개 문서를 완성 가능한 수준까지 끌어올리는 데 목적이 있다.

- `PRD`
- `Feature Spec`
- `Tech/API Spec`
- `Acceptance Criteria`

문서를 작성하거나 갱신하기 전에 반드시 [references/spec-template.md](references/spec-template.md)를 읽는다.

## Core Rules

- 기본 문서는 모두 한국어로 작성한다.
- 입력이 불완전하면 전체 문서를 한 번에 쓰지 말고 먼저 질문한다.
- 한 라운드에서 질문은 최대 3~5개만 한다.
- 질문 우선순위는 `범위 -> 사용자/행위자 -> 규칙/제약 -> 검증/실패 처리 -> 기술 계약` 순서로 둔다.
- 답변을 받을 때마다 초안을 갱신한다.
- 확정되지 않은 사항은 반드시 `열린 질문` 또는 `가정`에 남긴다.
- 근거 없이 결정을 지어 쓰지 않는다.
- 문장은 모호한 표현보다 테스트 가능한 문장으로 쓴다.
- 누락된 제약, 의존성, 경계 조건은 명시적으로 드러낸다.
- 사용자가 별도로 요청하지 않는 한 코드 구현이나 코드 생성으로 바로 넘어가지 않는다.

## Output Rules

- 기본 저장 위치는 `docs/specs/<feature-name>/`로 둔다.
- 최종 산출물은 아래 4개 파일로 분리한다.
  - `prd.md`
  - `feature-spec.md`
  - `tech-api-spec.md`
  - `acceptance-criteria.md`
- 초안 단계에서는 하나의 통합 초안으로 대화해도 되지만, 최종 정리는 파일 4개로 분리한다.
- 문서 메타데이터(`status`, `owner`, `updated_at` 등)는 기본 포함하지 않는다.
- 변경 이력, 결정 로그, ADR 링크, PR 링크 같은 관리 정보도 기본 포함하지 않는다.
- 그런 관리 정보는 사용자가 명시적으로 요청할 때만 추가한다.

## Workflow

### 1. 시작 지점을 올바르게 잡는다

- 사용자가 아이디어만 있으면 `Stage 1 - PRD`부터 시작한다.
- 사용자가 일부 문서를 이미 가지고 있으면 기존 내용을 보존하고 가장 먼저 비어 있는 단계부터 이어간다.
- 뒤 단계 정보가 먼저 나와도 버리지 말고 해당 섹션에 적어두되, 가장 앞 단계의 공백부터 메운다.

### 2. 질문 라운드를 돈다

각 라운드에서 다음 순서를 따른다.

1. 현재 이해한 내용을 짧게 요약한다.
2. 가장 영향력이 큰 질문 3~5개를 묻는다.
3. 답을 받으면 템플릿에 맞게 초안을 갱신한다.
4. 현재 단계가 충분히 구체화됐는지 다시 판단한다.
5. 다음 질문을 이어가거나 다음 단계로 넘어간다.

좋은 질문 우선순위 예시:

- 구현 세부보다 사용자 목표와 성공 조건
- 예외 케이스 나열보다 핵심 비즈니스 규칙
- 내부 모델보다 외부 계약과 인터페이스
- AC 작성보다 validation / permission / failure semantics

### 3. 단계별로 전진한다

- 텍스트가 조금 있다고 해서 다음 단계로 넘어가지 않는다.
- 현재 단계의 필수 항목이 모두 다음 둘 중 하나가 될 때만 다음 단계로 간다.
  - 사용자와 확정된 정보
  - 위험이 드러난 명시적 가정
- 아직 중요한 모호함이 남아 있으면 현재 단계에서 질문을 더 이어간다.

### 4. 최종 문서로 분리한다

최종 정리 시에는 반드시 문서를 아래처럼 분리한다.

- `prd.md`: 왜 만드는지, 누가 쓰는지, 성공이 무엇인지
- `feature-spec.md`: 실제 동작 흐름과 비즈니스 규칙
- `tech-api-spec.md`: 시스템 계약, validation, 에러, 데이터 영향
- `acceptance-criteria.md`: Given / When / Then 형식의 완료 기준

`PRD`가 작더라도 생략하지 않는다. 다만 내부 품질 개선 작업처럼 제품 기능이 아닌 경우에는 간결하게 작성한다.

## Stage Guide

### Stage 1 - PRD

반드시 수집하고 정리할 항목:

- `Goal`
- `Actor / User`
- `User Problem`
- `User Scenario`
- `Success Outcome`
- `Out of Scope`

질문 포인트:

- 이 문제를 직접 겪는 사람이 누구인가
- 무엇을 하려다가 막히는가
- 현재 방식이 왜 불편하거나 위험한가
- 성공을 어떤 관찰 가능한 결과로 볼 수 있는가
- 이번 단계에서 명시적으로 하지 않을 것은 무엇인가

주의:

- 성공 조건을 "좋아진다", "편해진다" 수준으로 두지 않는다.
- 관찰 가능한 결과나 판단 기준으로 좁힌다.

### Stage 2 - Feature Specification

반드시 정의할 항목:

- `Inputs`
- `Processing Flow`
- `Business Rules`
- `Permissions`
- `Edge Cases`

질문 포인트:

- 진입점은 어디인가
- 사용자 또는 시스템은 어떤 순서로 동작하는가
- 어떤 조건에서 분기되는가
- 역할별로 동작 차이가 있는가
- 중복 요청, 빈 상태, 부분 실패, 재시도 같은 경계 상황은 무엇인가

### Stage 3 - Technical / API Specification

반드시 정의할 항목:

- `System Interface`
- `Request Structure`
- `Response Structure`
- `Validation Rules`
- `Error Cases`
- `Data Model Impact`

질문 포인트:

- API, command, event, job, 내부 서비스 중 어디가 경계인가
- 동기 처리인가 비동기 처리인가
- 필수/선택 필드는 무엇인가
- validation 실패는 어떤 규칙과 응답으로 드러나는가
- 권한, 멱등성, 중복 처리 요구가 있는가
- 스키마, 저장 구조, 파생 필드에 어떤 영향이 있는가

주의:

- 기술 결정이 아직 없으면 억지로 확정하지 않는다.
- `열린 질문` 또는 `가정`으로 남긴다.

### Stage 4 - Acceptance Criteria

행동이 충분히 구체화된 뒤에만 작성한다.

반드시 포함할 범위:

- 정상 경로
- validation 실패
- 권한 차이
- 중요한 edge case
- out of scope라서 발생하면 안 되는 동작

주의:

- "정상 동작한다", "잘 작동한다" 같은 문장은 금지한다.
- 반드시 테스트 가능한 `Given / When / Then` 형식으로 쓴다.

## Draft Update Format

각 답변 라운드 이후에는 다음 형식으로 정리한다.

1. `현재 단계`
2. `확정된 정보`
3. `열린 질문`
4. `가정`
5. `갱신된 초안`
6. `다음 질문`(추가 질문이 남아 있을 때만)

규칙:

- `열린 질문`은 짧고 결정 지향적으로 쓴다.
- `가정`은 임시 결정임을 분명히 드러낸다.
- 초안이 비어 있는 섹션은 비워두지 말고, 왜 비어 있는지 `열린 질문`이나 `가정`으로 표현한다.

## Final Output

정보가 충분히 모이면 [references/spec-template.md](references/spec-template.md)의 구조를 따라 최종 문서를 작성한다.

최종 산출물 규칙:

- 한국어 문서 4개로 분리한다.
- 각 문서는 최소한 `확정된 정보`, `열린 질문`, `가정`을 포함한다.
- 미해결 사항이 남아 있으면 숨기지 말고 그대로 드러낸다.
- 완벽한 문서보다 모호함이 드러난 문서가 낫다.

문서 4종:

- `PRD`
- `Feature Spec`
- `Tech/API Spec`
- `Acceptance Criteria`
